# Tests

Two suites, which have nothing in common but the language they are written in.

| Suite | Configuration | Runs | Needs |
|---|---|---|---|
| Unit | `phpunit.xml` | In process, no I/O of any kind | Nothing but `composer install` |
| Integration | `phpunit-integration.xml` | Inside a disposable Docker stack, over real HTTP | Docker |

```bash
composer install

# The unit suite. Fast, hermetic, safe to run on every save.
vendor/bin/phpunit

# The integration suite. Brings a disposable stack up, runs, tears it down.
tests/docker/run.sh
```

PHPUnit is a `require-dev` dependency of this project and is run as `vendor/bin/phpunit`. That is deliberate: the
integration suite runs the library under four different PHP versions inside containers, and a PHPUnit installed on the
host would only ever be the host's.

## Layout

```
phpunit.xml                     The unit suite
phpunit-integration.xml         The integration suite
tests/
  bootstrap.php                 Unit bootstrap: the autoloader, and nothing else
  bootstrap-e2e.php             Integration bootstrap: the autoloader, and one probe that the stack is up
  config.dist.php               Committed defaults for the integration suite
  config.php                    Generated by run.sh from tests/docker/.env; git-ignored
  Stub/                         Test doubles shared by both suites
  Unit/                         The unit tests
  Integration/
    E2ETestCase.php             Base class: options, the three HTTP clients, the leak assertions
    Engine/FixtureControl.php   The test's own line to the fixture, out of band of the library
    Tests/                      The integration tests
  docker/
    docker-compose.yml          Services only. Never composed by hand.
    Dockerfile.web              The fixture server
    Dockerfile.client           The container the suite itself runs in
    env.dist                    Committed template; run.sh copies it to .env on first run
    run.sh                      The one supported entry point
    config/                     Apache vhost and php.ini for the fixture
    fixture/                    The fixture server's code
```

## The unit suite

In process, no network, no filesystem beyond a temporary directory or two. It covers the parts of the library which can
be reasoned about in isolation: the URI abstraction, the data objects, the options parsing, the URL and header
construction, the redirect policy, the response parsing, and every high level operation driven through a test double
standing in for the far end of the conversation.

```bash
vendor/bin/phpunit                          # everything
vendor/bin/phpunit --filter RedirectPolicy   # one class
```

## The integration suite

`tests/docker/run.sh` is the only supported way to run it. It scrubs whatever a previous run left behind, builds and
starts the stack, generates `tests/config.php`, runs PHPUnit inside the stack, and tears the stack down again. A run
which fails or is interrupted never leaves a stack behind in an unknown state.

| Option | Effect |
|---|---|
| `--php <version>` | Run under this PHP version instead of `E2E_PHP_VERSION` |
| `--matrix` | Run once under every version in `E2E_PHP_MATRIX` |
| `--filter <pattern>` | Passed straight through to PHPUnit |
| `--skip-build` | Reuse the Docker images as they are |
| `--keep-containers` | Leave the stack up afterwards, and reuse it if it is already up |
| `--down` | Tear the stack down and exit |
| `--no-tests` | Bring the stack up and provision it, but run nothing |

The fast loop is `--keep-containers --skip-build`, which reuses a stack that is already running and takes about a
second. Everything else scrubs first.

Settings live in `tests/docker/.env`, copied from `env.dist` on the first run. Change `E2E_PROJECT_NAME`,
`E2E_HTTP_PORT` and `E2E_SINK_HTTP_PORT` there if they collide with another local stack.

### Why the suite runs inside a container

The usual arrangement for an end-to-end suite is PHPUnit on the host driving an application in Docker. That does not
fit here, because the thing under test *is* the client. "Supported under PHP 8.2" means the library runs under PHP 8.2,
so the tests have to as well — which means the test runner is the thing whose PHP version the matrix varies, and it
belongs in a container.

Running inside the Compose network buys a second thing the host cannot offer: real host names. Docker's DNS resolves
every network alias below, so the redirect tests exercise the actual host comparison against actual hosts, rather than
against loopback addresses and a hosts file the suite would have to ask you to edit.

### The stack

| Service | Answers to | Is |
|---|---|---|
| `web` | `www.example.test`, `example.test`, `foobar.example.test`, `a.b.example.test`, `api.example.test` | The site under test |
| `evil` | `evil.test`, `shop.example.test`, `notexample.test`, `www.example.test.evil.test` | Somewhere the library must never go |
| `client` | — | The suite itself |

`web` runs a fixture which speaks all three versions of the JSON API — the v3 route under Joomla's API application in
both its rewritten and unrewritten forms, the v2 view on the site's front end, and the doubly encapsulated v1 — with
the authentication rules, response shapes and error statuses of the real thing. It is not Akeeba Backup and takes no
backups. It does not need to be: what the library does is talk to a server, and everything asserted here is observable
from this side of the conversation. It also does what a real server cannot be asked to do on demand, and what the
library exists to survive: redirect somewhere hostile, bury its answer in PHP warnings, or loop forever. Those are
armed one request at a time through `control.php`, which the tests drive with bare cURL rather than through the library.

`evil` runs the same fixture and records every request it receives. That is what turns "the redirect was refused" into
an assertion about the world: each refusal test asserts both that the library refused and that nothing was ever
delivered to the other end. The second half is the one that fails when the guard is missing — verified by taking
`isRedirectAllowed()` out and watching eighteen tests fail and the sink's phishing response arrive at the client.

Both fixture containers keep their state in a file inside the container. Nothing here touches a database, a mail
server, or anything that outlives `docker compose down`.

### The version matrix

`composer.json` declares `"php": ">= 8.2.0 < 8.7"`. The floor of the matrix is that minimum; the ceiling is the newest
release that exists. That gives **8.2, 8.3, 8.4 and 8.5**, and a no-flag run uses 8.5.

Every interior version earns its place, because this library reaches for things whose behaviour has moved recently:
`curl_close()` is a no-op from 8.0 and deprecated from 8.5, the nullsafe operator's interaction with undefined array
keys is what one skipped test below records, and the Joomla Framework HTTP response object changed shape between major
versions of `joomla/http`. A single-version run would prove none of that.

The *server's* PHP version, `E2E_SERVER_PHP_VERSION`, is not part of the matrix and does not need to be. It only has to
be new enough to run the fixture.

Matrices go stale as soon as a new PHP release ships or the project's own declared floor moves. Re-check this with the
`audit-e2e-matrix` workflow rather than editing the numbers by hand.

### What the integration suite does not cover

* **TLS, and therefore the refusal to be downgraded from HTTPS to plaintext HTTP.** The stack speaks HTTP only, so the
  downgrade rule is covered by the unit suite alone.
* **The cURL download mode.** It shells out to `curl_exec()` against a URL the caller supplies, entirely outside the
  library's HTTP client abstraction, so there is nothing about it the fixture would exercise that the HTTP and chunked
  modes do not.
* **Proxy support.** `HttpClientGuzzle` can be given proxy settings; the stack has no proxy in it.

## Skipped tests

Eleven unit tests and six integration tests are skipped, every one of them recording a defect in the library rather
than a gap in the suite. Each carries the diagnosis and the fix in its docblock. In rough order of severity:

| Where | What |
|---|---|
| `AbstractHttpClient::removeResponseJunk()` | Junk *after* the JSON is not stripped, and the recovery loop then destroys the payload. `substr()` is given an offset where it wants a length. |
| `HighLevel\DeleteFiles` | The failure path passes the server's error text where a `?Throwable` is expected, so a failed `deleteFiles()` raises a `TypeError` instead of the documented exception. |
| `HighLevel\Autodetect::getEndpoints()` | Only `index.php` is ever probed, so autodetect cannot find an Akeeba Solo or Akeeba Backup for WordPress site unless the caller pasted the endpoint. |
| `Options::parseHost()` | A host with no scheme — the form this library's own README passes — loses its host name and yields `http:///`. |
| `HighLevel\Autodetect::getVerbs()` | Only `GET` is ever probed, for the same reason as the endpoints. |
| `HighLevel\Download::downloadHTTP()` | Raises "Undefined array key" warnings before refusing a part the server did not describe. |
| `Uri::setQuery()` | `parse_str()` cannot write into a magic property, so the method silently does nothing. |
| `Options` | The `debug` alias of `verbose` is unreachable. |

Unskipping is the last step of fixing any of them: each test already asserts the behaviour the fix should produce.
